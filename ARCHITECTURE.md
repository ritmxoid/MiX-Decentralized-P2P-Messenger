# Архитектура децентрализованного анонимного мессенджера MiX

## 1. Общая концепция и принципы

**MiX** — автономный P2P-мессенджер с распределённым зашифрованным хранилищем. В системе отсутствуют обязательные централизованные серверы регистрации, базы данных пользователей, облачные хранилища файлов или сторонние провайдеры аутентификации.

Главный принцип: **пользователь владеет своей цифровой идентичностью, ключами, сообщениями и ресурсами, которые он добровольно выделяет сети.**

## 2. Модульная структура проекта

```
server.ts                               # Опциональный stateless-узел рандеву/ретрансляции (WebSocket /ws/p2p, без БД)
src/
  App.tsx                               # Корневая оболочка и маршрутизация экранов
  modules/
    types.ts                            # Протокольные типы и контракты модулей
    MixNodeController.ts                # Оркестратор взаимодействия 11 модулей
    identity/IdentityModule.ts          # Генерация Ed25519/X25519, DID, анти-Sybil PoW, резервные копии .mixkey
    auth/AuthModule.ts                  # Локальная аутентификация на Argon2id + AES-256-GCM
    crypto/CryptoModule.ts              # Ed25519, X25519, HKDF-SHA256, AES-256-GCM, GF(2^8) Reed–Solomon
    p2p/P2PNetworkModule.ts             # BroadcastChannel Mesh + WebRTC DataChannel + Circuit Relay
    discovery/DiscoveryModule.ts        # Kademlia XOR-distance DHT для поиска @login и держателей блоков
    messaging/MessagingModule.ts        # Личные и групповые E2EE-чаты, ротация ключей, Store-and-Forward
    storage/DistributedStorageModule.ts # IndexedDB-хранилище с жёстким контролем квот и TTL
    fileTransfer/FileTransferModule.ts  # Шифрование, фрагментация, RS-избыточность, параллельная сборка
    replication/ReplicationModule.ts    # Скоринг узлов, аудит доступности и самовосстановление блоков
    metadata/MetadataModule.ts          # Многоступенчатый Onion-маршрут, padding корзин, timing jitter
    security/SecurityModule.ts          # Rate limiter, репутация узлов, карантин, проверка SHA-256/подписей
    ui/                                 # 12 экранов пользовательского интерфейса
```

## 3. Криптография и сквозное шифрование (E2EE)

Используются только проверенные стандартизированные примитивы (`@noble/curves`, `@noble/hashes`, Web Crypto API):

1. **Идентичность**:
   - `Ed25519` (RFC 8032) — подпись публичной карточки, записей DHT и конвертов сообщений.
   - `X25519` (RFC 7748) — согласование общего секрета (ECDH) для переписки, групповых ключей и слоёв луковой маршрутизации.
   - `DID` формируется детерминированно: `mix:<первые 32 hex-символа SHA-256(Ed25519PublicKey)>`.
2. **Локальное хранилище ключей**:
   - Ключ шифрования связки выводится из пароля через **Argon2id** (`m = 16 MiB, t = 2, p = 1`, 16-байтная случайная соль).
   - Приватные ключи и локальная история переписки хранятся в IndexedDB в зашифрованном виде (`AES-256-GCM`).
3. **Личные и групповые чаты**:
   - Личные сообщения: `X25519(myPriv, peerPub)` -> `HKDF-SHA256` -> `AES-256-GCM` + подпись `Ed25519` + монотонный счётчик `seq` и `nonce` против повтора.
   - Группы: симметричный 256-битный ключ группы (`keyEpoch`). При добавлении или удалении участника ключ **немедленно ротируется** (`keyEpoch + 1`) и рассылается только актуальному составу через `X25519`.

## 4. Распределённое зашифрованное хранилище и Reed–Solomon

1. Исходный файл шифруется уникальным 256-битным ключом `fileKey` (`AES-256-GCM`) на устройстве отправителя.
2. Шифртекст кодируется систематическим кодом **Коши Рида–Соломона над полем $GF(2^8)$** (`k = 4` блока данных + `m = 2` блока чётности).
3. Для каждого из 6 блоков вычисляется `SHA-256` идентификатор (`shardId`).
4. Модуль `ReplicationModule` ранжирует доступные узлы по свободному месту, репутации, RTT, времени работы и уровню заряда батареи и распределяет блоки между разными узлами.
5. **Отказоустойчивость**: потеря или отключение любых **2 из 6 узлов** не приводит к потере файла — получатель восстанавливает шифртекст из любых 4 валидных блоков и расшифровывает файл локально. Владельцы узлов хранения видят только непрозрачные зашифрованные байты.

## 5. P2P-сеть, NAT traversal и ограничения браузера / Android

### Как работают соединения
- **Локальная шина (`BroadcastChannel`)**: нулевая зависимость от серверов при взаимодействии между вкладками/окнами одного устройства.
- **Прямой P2P (`WebRTC DataChannel`)**: прямое соединение между разными браузерами и устройствами с ICE/STUN.
- **Добровольный узел рандеву и ретрансляции (`server.ts`)**: абсолютно stateless WebSocket-ретранслятор без базы данных и дисков. Нужен только для обмена SDP/ICE и резервной пересылки зашифрованных конвертов через строгий симметричный NAT.

### Ограничения NAT и мобильной ОС Android
1. **CGNAT / Симметричный NAT**: в сотовых сетях прямое соединение между двумя смартфонами без промежуточного ретранслятора часто невозможно. В этой ситуации ретрансляцию выполняют добровольные узлы сети (`Circuit Relay`), не имея доступа к ключам E2EE.
2. **Android Doze / App Standby**: мобильная ОС агрессивно приостанавливает фоновую работу. Для полноценного мобильного клиента на Android (Kotlin / Jetpack Compose + libp2p / Briar-style BLE/Wi-Fi Direct) требуется `Foreground Service` с уведомлением для активной передачи, `WorkManager` для периодического аудита блоков, а круглосуточную доступность узла хранения рекомендуется возлагать на ПК, домашние серверы или NAS.
3. **Ограничения веб-прототипа**: в браузерной среде недоступны raw UDP/QUIC-сокеты и системный `libp2p` TCP/mDNS транспорт — вместо них реализованы честные браузерные P2P-транспорты (`WebRTC DataChannel` + `BroadcastChannel` + stateless `WebSocket` relay).

## 6. Защита метаданных: честная модель угроз

- **Что защищено**:
  - Узлы хранения не могут прочитать содержимое файлов и узнать их имена.
  - Промежуточные узлы при включённой 2-хоповой луковой маршрутизации видят только соседний хоп и выровненный размер пакета (`1 / 4 / 16 / 64 КБ`).
- **Что ограничено**:
  - Если включён прямой `WebRTC`, ICE-кандидаты раскрывают IP-адрес собеседнику. Для скрытия IP от собеседника необходимо отключать прямой WebRTC и использовать ретрансляцию через промежуточные узлы.
  - Глобальный пассивный наблюдатель (провайдер уровня AS/ISP), контролирующий вход и выход трафика, способен проводить временную корреляцию; для защиты от такого уровня угроз на Android/Desktop потребуется интеграция внешнего микснета (Tor / Nym).
